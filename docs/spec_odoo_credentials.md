# Spec: Odoo connection settings for the tray hub

Status: agreed 2026-09-29; built 2026-10-01 on branch `feat/odoo-connection`. Technical spec.

## Goal

The tray app gives the hub it starts an Odoo connection:
- `ODOO_URL` and `ODOO_DB`;
- `ODOO_USER` and `ODOO_PASSWORD` for a user dedicated to that hub.

The password is kept in the OS keychain, not in a plain file.

This fixes two problems:
1. **Plain-text passwords.** Credentials sat in files or environment variables that anyone at the restaurant PC could read.
2. **One shared Odoo user.** All hubs signed in as the same user, so you couldn't tell hubs apart or cut off just one.

It is also a prerequisite for bumping the tray's bundled hub past monorepo v0.14. From that version (rost_pos_restaurant#168), the hub exits with code 78 when `ODOO_USER`/`ODOO_PASSWORD` are empty or the password is `admin`.

## Constraints

- **Who installs hubs:** our team only, fewer than 10 hubs over the next 12 months. Setup speed doesn't matter.
- **Platforms:** Windows and Linux desktop. Whether the Linux machines run GNOME/KDE with a working Secret Service is unknown.
- **Existing installs:** no tray hubs are in real use, so nothing needs migrating.
- **No Odoo changes.** The hub keeps signing in with a user and password over RPC, which is all Odoo 12 supports (it has no API keys).
- **Hub code** (`nu_pos_hub`) is unchanged.

## Approach

### Odoo side (manual, documented)

For each hub, an admin creates a user, for example `hub-barilo`:
- with the POS rights the hub needs, plus the **POS Hub Service** group, so the hub can read the offline-login data;
- with a long random password, generated by whoever sets it up and entered once in the tray.

To cut off a hub, archive its user.

### Tray: settings split

- **`settings.json`** (not secret): `odoo_url`, `odoo_db`, `odoo_user`.
- **OS keychain** (secret): the password, through the `keyring` crate.
  - Service name: `sirvo-hub-tray`.
  - Account: `<odoo_url>|<odoo_db>|<odoo_user>`.
- **Windows:** Credential Manager, which encrypts the secret to the logged-in Windows user.
- **Linux:** Secret Service (GNOME Keyring or KWallet).
  - **Fallback:** if the keychain is unavailable or locked, store the password in `odoo-secret` in the app config folder, with mode `0600`.
  - The tray shows "stored in a protected file (keychain unavailable)" so this is visible.

### Tray: setup form

- **When it appears:** from the tray menu ("Odoo connection…"), and automatically when the credentials are missing.
- **Fields:** URL, database, user, password.
- **"Test and save"** does these checks before storing anything:
  1. Call `/web/session/authenticate` with those values; a failed login is shown to the user.
  2. Refuse the password `admin` (the same rule as the hub's `validateConfig`).
  3. Check that the user is in POS Hub Service. If not, show a warning, not an error: the hub still works, only without offline logins.
- **On success:** save, then restart the hub.
- **Password field:** always shown blank when editing. Leaving it blank keeps the stored password.

### Tray: starting the hub

- **Normal start:** `Supervisor::start` reads the settings and the stored password, and passes all four variables with `.env(...)`, next to the existing ones in `supervisor.rs:78-81`.
- **Credentials missing:** don't start the hub. Set the state to a new `NeedsSetup`, and open the form.
- **Exit code 78** (the hub's `EXIT_CONFIG_ERROR`):
  - don't auto-restart;
  - set the state to `ConfigError`;
  - show the hub's last `hub_config_error` log line and a button that opens the form.

### Release order

1. Build and release the tray with this change while it still bundles hub v0.13.0. That hub ignores the new variables, apart from actually connecting to the real Odoo.
2. Configure each tray machine.
3. Bump the bundled hub to v0.15 or later.

## Non-goals

- **Pairing / device-code / OAuth flows.** Their benefit is setup convenience, which isn't a problem at this scale. Reconsider if Sirvo goes to outside customers (see "Later").
- **Odoo endpoints or models.**
- **Token-based hub → Odoo authentication.** It would require moving `forwarder`, `floorPlanFetcher` and `offlineAuthSync` off RPC. Deferred, possibly to the Odoo 18 move, which has API keys.
- **systemd and Docker hubs.** They keep `/etc/pos-hub/env` (root-only, `0600`) or container environment variables, with a per-hub user. This spec only documents that.
- **Importing existing `ODOO_*` environment variables.** No tray hub is in use.

## Open questions

1. **Which Odoo rights does the hub user need?** Pin down the minimum groups for order forwarding, the floor plan and the offline snapshot, instead of copying whatever the current shared user has.
2. **Linux tray machines:** confirm whether they have a desktop with Secret Service. That decides whether the `0600` fallback is the normal path or the exception.
3. **Password rotation:** is "change it in Odoo, then re-enter it in the tray" enough, or should the form offer "generate a new password"? That would need an Odoo call with admin rights, which puts it outside this scope.

## Later (if Sirvo goes multi-tenant)

A single-use setup code generated in Odoo, which the tray redeems for a random password nobody sees. The per-hub user would be created automatically. This builds on this spec without replacing it.
